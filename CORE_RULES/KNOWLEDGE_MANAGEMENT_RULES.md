# 知识库管理规范

## 1. 目标

知识库用于沉淀 AI Software Studio 在产品开发、问题处理、架构设计、测试和用户验收过程中形成的可复用经验。知识内容必须准确、可检索、可验证，并避免记录未经确认的推测。

本规范只定义知识分类和管理方式；具体项目知识应在对应项目完成验证或复盘后再行归档。

## 2. 知识来源

知识可以来源于：

- 项目开发问题。
- Bug 修复记录。
- 架构经验。
- 测试经验。
- 用户反馈。

所有知识条目都应说明来源背景、适用范围和验证状态。涉及具体项目时，应关联对应项目、版本、报告或 Git 记录。

## 3. 分类规则

### DEVELOPMENT_LESSONS

用于记录开发过程经验，包括有效实践、失败教训、效率改进和工程约束。

每条记录建议包含：

- 背景与目标。
- 采取的做法。
- 实际结果。
- 经验结论。
- 适用与不适用范围。

### BUG_CASES

用于记录具有诊断价值或复用价值的 Bug 案例。

每条记录必须包含：

- 问题现象。
- 原因分析。
- 修复方案。
- 防止再次发生的方法。

还应尽可能记录影响范围、复现条件、验证结果和关联版本。

### ARCHITECTURE_PATTERNS

用于记录经过验证、可在多个项目或模块中复用的架构方案。

每条记录建议包含：

- 方案要解决的问题。
- 适用场景与前置条件。
- 核心结构和模块边界。
- 关键设计决策。
- 优点、限制和风险。
- 验证方式与参考实现位置。

### TEST_CASE_LIBRARY

用于记录可复用的测试场景，包括功能、边界、异常、回归和自动化测试场景。

每条记录建议包含：

- 测试目标。
- 前置条件。
- 输入与操作步骤。
- 预期结果。
- 适用范围。
- 自动化建议。

### PROJECT_RETROSPECTIVES

用于记录项目完整复盘，呈现目标、实际结果、问题、解决方案和后续改进。

复盘记录应基于真实项目结果，并至少关联项目版本、验收结论和发布报告。

## 4. 归档规则

1. 一条知识只归入最主要的分类；需要跨分类引用时使用链接，避免重复副本。
2. 文件名应清晰表达主题，不使用无意义编号或临时名称。
3. 归档前应确认事实、原因、方案和验证结果，不将未验证猜测作为结论。
4. 不记录密钥、密码、个人敏感信息或其他不应进入版本库的数据。
5. 已失效的知识不得直接删除，应标明失效原因、替代方案和适用版本。
6. 知识更新应通过 Git 记录保留变更历史。

## 5. 质量要求

知识条目应满足：

- 可理解：背景和术语清楚。
- 可验证：结论有结果或证据支持。
- 可复用：说明适用范围和使用条件。
- 可追踪：能够关联来源、版本或报告。
- 可维护：内容发生变化时可以明确更新。
