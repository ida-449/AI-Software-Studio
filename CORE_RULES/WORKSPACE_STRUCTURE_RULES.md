# AI Software Studio 工作区结构规范

## 1. 目标与适用范围

本规范用于明确 AI Software Studio 工作室仓库与业务项目之间的关系，确保规则、模板、知识和项目交付物各自归位，并在多项目、多设备协作中保持清晰边界。

## 2. AI Software Studio 定位

AI Software Studio 是软件产品开发的治理与能力中心，承担以下职责：

- 开发规范中心：维护项目生命周期、开发规则、阶段门禁和治理要求。
- 模板中心：提供 PRD、技术方案、风险评估、开发计划、测试、验收、发布和复盘模板。
- 知识中心：沉淀开发经验、Bug 案例、架构模式、测试场景和项目复盘。
- AI 团队管理中心：定义产品、技术、开发、测试和用户验收角色的职责与协作方式。

AI Software Studio 不直接存放业务代码。工作室根目录及其治理目录不得承载具体产品的实现文件。

## 3. PROJECTS 定位

`PROJECTS/` 是业务项目的统一入口。每个业务项目必须独立管理，使用唯一、清晰的项目目录，不与其他项目混合文件、依赖或交付物。

标准结构如下：

```text
PROJECTS/
└── <PROJECT_NAME>/
    ├── docs/
    ├── src/
    ├── tests/
    ├── reports/
    └── README.md
```

各目录职责：

- `docs/`：保存该项目的需求、技术方案、风险评估和开发计划。
- `src/`：保存该项目的业务代码。
- `tests/`：保存该项目的自动化测试、测试数据和测试支持文件。
- `reports/`：保存该项目的测试、验收、发布和复盘报告。
- `README.md`：说明该项目的目标、范围、环境、使用方式、当前版本和维护信息。

业务代码只能存放在对应项目的 `src/` 范围内，不得进入 `CORE_RULES/`、`ROLES/`、`KNOWLEDGE_BASE/`、`TEMPLATES/` 或工作室级 `REPORTS/`。

## 4. 工作模式

### 工作室

工作室负责提供：

- 标准流程和治理规则。
- 可复用文档模板。
- AI 团队角色与协作边界。
- 经验证的开发、架构和测试经验。
- 跨项目使用的知识与质量基线。

### 项目

项目负责具体产品开发，包括：

- 记录和确认具体业务需求。
- 形成项目级产品与技术文档。
- 实现、测试和验收业务功能。
- 管理项目版本、发布和回滚。
- 输出项目报告，并将可复用经验反馈到工作室知识体系。

工作室规则指导项目，项目实践反哺工作室；项目内容不得反向污染工作室的通用规范和模板。

## 5. 多设备使用

AI Software Studio 通过 Git 进行版本管理和设备间同步。

在不同电脑使用时，应 clone 同一个 AI Software Studio 仓库，并基于同一远程版本开展工作。不得通过手工复制部分规则文件的方式建立长期分叉副本。

多设备协作必须保持：

- 规则一致：所有设备使用仓库中已提交的同一套规范和模板。
- 版本一致：开始工作前确认分支、commit 和工作区状态，并同步所需更新。

推荐流程：

1. 在目标电脑 clone 同一个仓库。
2. 开始任务前确认项目路径、当前分支、commit 和 Git 状态。
3. 获取并审阅远程更新，避免覆盖本地未提交内容。
4. 完成变更后进行检查、提交并同步到约定的远程仓库。
5. 切换设备前确认必要变更已经提交并可追踪。

密钥、密码、设备专属配置和个人敏感信息不得通过仓库同步。

## 6. 项目隔离

每个业务项目必须保持目录、代码、测试、依赖、配置和报告边界清晰。

禁止：

- 一个项目修改另一个项目的代码。
- 未经授权读取、复制或复用另一个项目的专属业务实现。
- 将多个项目的业务代码放入同一个 `src/` 目录。
- 为完成当前项目任务而顺带修改其他项目文件。
- 将项目专属规则直接写入工作室通用规范。

如确需跨项目变更，必须分别明确每个受影响项目的需求、授权、修改范围、风险、测试和 Git 记录，不得以单一项目任务隐含授权其他项目修改。

## 7. 执行要求

开始任何项目工作前，AI 团队必须确认：

- 当前位于工作室还是具体项目目录。
- 当前任务属于工作室建设还是业务项目开发。
- 目标文件属于正确的目录和项目。
- Git 状态、当前版本和修改授权范围已经明确。

发现目录错位、项目边界不清或可能发生跨项目修改时，应停止操作，先输出诊断并澄清范围。
