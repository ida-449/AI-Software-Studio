# AI Software Studio 角色交接协议

## 1. 原则

角色是同一交付流程中的责任阶段，不是互相丢任务的独立人员。每次交接必须基于可检查产物和明确状态，禁止只用“已完成”“应该可以”等主观描述。

## 2. 标准状态

- `ready`：输入完整，允许下一角色开始。
- `in_progress`：当前角色正在执行。
- `failed`：存在可复现失败，回到诊断与开发循环。
- `blocked`：存在 AI 无法自行解除的真实外部阻塞。
- `passed`：本阶段证据满足出口条件。

`failed` 不得直接交给用户；AI 团队内部继续诊断和修复。只有 `blocked` 涉及必要授权或业务决策时才请求用户。

## 3. 交接包

每次交接至少包含：

- 任务目标与验收标准。
- 项目绝对路径、分支、基线 commit 和工作区状态。
- 本阶段修改文件与影响范围。
- 已执行命令、退出码与结果摘要。
- 失败、未覆盖项、剩余风险和回滚点。
- 下一角色允许执行的范围与禁止事项。

使用 `TEMPLATES/ROLE_HANDOFF_TEMPLATE.md` 记录需要持久化的里程碑交接；小型任务可在内部使用等价结构，不制造无价值文档。

## 4. 角色出口条件

### 产品经理 → 技术负责人

需求范围、非目标、优先级和可验证验收标准已确认。

### 技术负责人 → 开发工程师

技术方案、模块边界、风险、高风险操作和测试策略已明确。

### 开发工程师 → 测试工程师

实现范围明确，开发自检完成，相关测试已建立，代码可构建或已说明阻塞。

### 测试工程师 → 开发工程师

发生失败时必须返回可复现证据、失败阶段和影响范围，不直接给出未经验证的猜测修复。

### 测试工程师 → 发布经理

`full` 质量门禁通过，失败项为零，未覆盖项和限制已明确。

### 发布经理 → 用户体验验收

Git、安全、版本、回滚和交付检查通过，用户拿到的是可直接体验的成果，不是调试任务。

## 5. 禁止事项

- 禁止用文档签字代替真实命令执行。
- 禁止测试工程师自行放宽验收标准让失败变通过。
- 禁止开发工程师删除失败测试来消除红灯。
- 禁止发布经理在门禁失败时提交业务里程碑。
- 禁止把代码运行、依赖安装、日志分析和常规调试交给用户。
