# AI Software Studio 可执行质量门禁

## 1. 目标

将“应当测试”转化为可执行、可复现、可审计的通过证据。门禁只能证明已定义范围内的检查通过，不得宣称软件绝对没有缺陷。

## 2. 项目配置

每个外部业务项目应在项目内维护 `.ai/quality-gate.json`，格式参考 `TEMPLATES/PROJECT_QUALITY_GATE.example.json`。配置由 AI 根据项目真实技术栈建立，不要求用户填写命令。

检查按以下标准阶段排序：

1. `format`：格式检查，不在门禁中自动改写文件。
2. `lint`：静态规则与明显缺陷。
3. `typecheck`：类型与编译前一致性。
4. `test-related`：与本次变更直接相关的测试。
5. `test-full`：全量自动测试。
6. `build`：可交付构建。
7. `smoke`：启动与关键路径冒烟验证。
8. `dependency-audit`：未使用、重复、漏洞或异常依赖检查。
9. `cleanliness`：调试残留、生成物、死代码和任务范围检查。
10. `sensitive-scan`：敏感文件名、凭据、业务数据和大文件检查。

项目没有某阶段时必须标记 `not_applicable` 并说明原因，不能用“未配置”等同于“通过”。

## 3. 快速与完整门禁

- `quick`：每轮修复后运行，至少包含静态检查、类型检查、相关测试和构建中适用的项目。
- `full`：里程碑、收工和发布前运行，包含全部适用阶段及回归检查。
- 任一必需检查失败，门禁立即变为 `failed`，禁止提交业务里程碑或进入发布。
- 门禁报告必须包含项目路径、基线 commit、检查命令、退出码、耗时、结果和失败摘要。

## 4. 测试失败修复闭环

测试或运行失败后，AI 必须持续执行：

1. 固定失败命令、退出码、关键错误、环境和复现条件。
2. 判断故障属于代码、测试、依赖、环境还是外部服务。
3. 定位根因，不以重复运行代替诊断。
4. 设计最小修复范围，并检查是否会影响高风险边界。
5. 修复代码，同时补充或修正能证明根因的测试。
6. 重跑首次失败检查，证明本次修复有效。
7. 运行受影响范围回归，再运行 `full` 门禁。
8. 若仍失败，以新证据进入下一轮；不得隐藏、跳过或改成非必需检查。

循环直到门禁通过，或遇到身份授权、系统安装、外部服务不可用、关键业务冲突、数据风险或不可逆操作等真实阻塞。真实阻塞必须输出证据和下一步，不得把常规排错转交用户。

## 5. 代码整洁门禁

AI 必须检查：

- 未使用依赖、导入、变量和不可达代码。
- 重复实现、废弃文件和无调用入口。
- 临时调试输出、测试专用开关、注释掉的大段代码。
- 意外生成物、缓存、日志、大文件和超出任务范围的变更。
- 被跳过、失效或没有断言的测试。
- 依赖锁文件变化是否与任务一致。

工具报告只作为证据之一。删除疑似冗余代码前仍须确认无运行时、反射、配置或外部调用依赖。

## 6. 安全边界

- 门禁命令只能来自当前项目内已审阅的质量配置。
- 门禁不得包含真实外部提交、删除业务数据、生产部署或修改账号权限。
- 高风险操作必须保持独立授权，不能因测试脚本返回成功而视为已授权。
- 业务项目的门禁报告默认保存在本地，不因执行门禁获得上传授权。

## 7. 通过条件

只有同时满足以下条件才能标记 `passed`：

- 所有必需检查退出码为 0。
- 所有不适用项都有明确、可信的原因。
- 没有未解释的测试跳过、敏感信息或范围外改动。
- 本次失败对应的回归测试已经执行。
- Git diff 与门禁所验证的代码一致。
