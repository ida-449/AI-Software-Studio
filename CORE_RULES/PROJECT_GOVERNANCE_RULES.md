# 项目启动与治理规范

## 1. 适用范围

本规范适用于 AI Software Studio 未来启动和管理的所有项目。每个项目必须遵循统一的生命周期、启动检查、阶段门禁、目录标准和版本管理规则。

本规范不授权创建具体业务项目。项目只有在用户明确批准启动后，才能在 `PROJECTS/` 下建立对应目录，或作为外部独立 Git 仓库登记到 `PROJECTS/PROJECT_REGISTRY.md`。

## 2. 项目生命周期

### 阶段 0：需求输入

目标：接收并准确记录用户提出的业务问题、目标和期望结果。

输出：

- 用户需求描述。

进入下一阶段前必须确认需求来源和原始表达已被完整记录。

### 阶段 1：需求分析

目标：澄清用户目标、使用场景、功能边界、非功能要求和验收标准。

输出：

- `PRD`。

进入下一阶段前必须由产品经理确认 PRD 可用于技术设计，并由用户确认需求方向。

### 阶段 2：技术设计

目标：定义系统架构、模块边界、数据结构、接口、技术选型和兼容性方案。

输出：

- `TECH_DESIGN`。

进入下一阶段前必须确认技术方案覆盖已批准需求，且关键设计决策可解释、可实施。

### 阶段 3：风险评估

目标：识别技术、数据、安全、业务、进度和兼容性风险，并制定处理措施。

输出：

- `RISK_ASSESSMENT`。

进入下一阶段前必须明确阻塞风险、剩余风险及其接受状态。

### 阶段 4：开发计划

目标：拆分阶段和任务，明确优先级、负责人角色、依赖、产出与验收节点。

输出：

- `DEVELOPMENT_PLAN`。

进入下一阶段前必须确认任务范围、执行顺序、测试安排和交付条件。

### 阶段 5：开发实施

目标：依据已确认的需求、技术方案、风险措施和开发计划完成实现。

输出：

- 功能实现。
- 配套测试。
- Git 变更记录。
- 开发自检结果。

开发过程中不得擅自扩大范围；发现需求或方案问题时，应停止相关实现并返回对应阶段处理。

### 阶段 6：测试验收

目标：验证功能正确性、异常处理、边界行为和原有功能稳定性，并完成 AI 内部验收与用户体验验收。

输出：

- 测试报告。
- AI 内部验收结论。
- 用户体验验收结论。
- 已知风险清单。

未通过项必须得到修复、重新验证，或获得明确的风险接受。

### 阶段 7：发布

目标：以可追踪、可验证、可回滚的方式交付已验收版本。

输出：

- 发布版本。
- 发布报告。
- Git commit 或版本标签。
- 回滚方案。

发布后必须执行基本可用性检查，并记录实际发布结果。

### 阶段 8：复盘

目标：总结目标达成情况、问题、解决方案和可复用经验，推动规则与知识体系持续改进。

输出：

- 项目复盘报告。
- 知识库沉淀项。
- 后续优化项。

## 3. 项目启动检查清单

项目开始前必须完成以下确认。任何阻塞项未解决时，不得进入开发实施阶段。

### 环境

- [ ] 已确认项目绝对路径。
- [ ] 已确认操作系统及版本。
- [ ] 已确认开发环境、工具链和关键依赖。
- [ ] 已确认读取、写入、执行及其他必要权限。

### 版本

- [ ] 已确认 Git 状态，已识别所有未提交变更。
- [ ] 已记录当前 commit。
- [ ] 已确认当前分支及目标分支。

### 需求

- [ ] 已确认用户目标。
- [ ] 已确认功能范围。
- [ ] 已确认不做范围。

### 技术

- [ ] 已确认架构方案。
- [ ] 已确认数据方案，包括存储、迁移、备份和安全要求。
- [ ] 已识别风险并制定处理措施。

## 4. 阶段门禁规则

以下门禁为强制规则：

- 禁止需求未确认进入开发。
- 禁止技术方案未完成进入编码。
- 禁止测试未通过进入发布。
- 禁止用户未验收进入正式使用。

门禁检查必须基于阶段输出和明确结论，不得以口头假设、未验证结果或计划执行代替实际完成。

如确需例外，必须由用户明确批准，并记录原因、影响范围、风险、补偿措施和后续完成时间。

## 5. 项目目录标准

工作室内托管的正式项目位于 `PROJECTS/` 下；已有外部独立仓库可保留原位置，但必须在注册表记录设备路径、远程、版本和同步状态。每个项目使用独立目录：

```text
PROJECTS/
└── <PROJECT_NAME>/
    ├── docs/
    ├── src/
    ├── tests/
    ├── reports/
    └── README.md
```

目录职责：

- `docs/`：保存 PRD、技术方案、风险评估和开发计划等项目文档。
- `src/`：保存业务实现代码。
- `tests/`：保存自动化测试、测试数据和测试支持文件。
- `reports/`：保存测试、验收、发布和复盘报告。
- `README.md`：说明项目目标、范围、环境、启动方式、版本和维护信息。

不得将不同项目的业务代码或项目文档混放在同一项目目录中。

## 6. 本地备份与远程同步

- AI Software Studio 自身可在安全检查通过后自动 commit 并 Push。
- 外部独立业务项目默认只做适用测试、状态更新、本地 commit 和本地备份，不自动创建远程仓库、不 Push、不上传代码。
- 只有用户明确要求上传业务项目时，才允许启动远程同步；授权不替代敏感信息、大文件、未跟踪文件和完整 Git 历史审计。
- 业务项目的具体账户、产品、客户、素材和真实数据不得复制进工作室；仅匿名、跨项目可复用经验可进入工作室知识库。

## 7. 版本管理规则

### 版本格式

项目版本采用：

```text
Major.Minor.Patch
```

正式版本标签使用 `v` 前缀，例如：

```text
v1.0.0
```

### 版本含义

- `Major`：重大架构变化、破坏性变更或不兼容升级。
- `Minor`：向后兼容的新增功能或显著能力扩展。
- `Patch`：向后兼容的 Bug 修复或小范围质量改进。

### 管理要求

1. 每次发布必须具有明确版本号。
2. 版本号必须与实际变更性质一致。
3. 发布版本必须关联 Git commit；正式发布建议创建对应 Git tag。
4. 发布报告必须记录上一版本、当前版本、修改内容、测试结果、已知风险和回滚方案。
5. 未发布变更不得冒用已发布版本号。
