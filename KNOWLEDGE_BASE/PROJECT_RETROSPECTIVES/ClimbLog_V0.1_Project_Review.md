# ClimbLog V0.1 项目复盘

> 复盘日期：2026-07-16  
> 项目阶段：V0.1 本地 Web 原型  
> 项目状态：核心记录流程可体验，完整 V0.1 尚未发布

## 一、项目概述

### 项目目标

ClimbLog 是面向攀岩爱好者的个人训练助手，以单条线路为记录单位，帮助用户记录抱石与难度攀登训练，并通过历史与统计观察成长。首版要求完全本地运行，不连接外部接口，界面简洁、美观、大方。

### 用户痛点

- 训练记录分散，难以长期维护。
- 训练后难以回顾线路难度、完成状态与尝试次数。
- 抱石和难度攀登使用不同难度体系，普通表格容易混淆。
- 缺少直观的训练频率、完成率和难度趋势反馈。
- 用户希望降低记录步骤，同时保护个人训练数据。

### 最终实现情况

已完成的可体验原型能力：

- React + TypeScript + Vite 本地 Web 工程。
- 移动端优先的快速记录界面。
- V Scale 与法国难度体系。
- Onsight、Flash、Send、Attempt 领域规则。
- IndexedDB 本地持久化。
- 记录新增、查询、删除和类型筛选。
- 线路数、完成数和完成率基础统计。
- 16 项自动化测试、lint 和生产构建验证。

尚未完成：

- 记录编辑。
- 完成状态与难度筛选。
- 完整成长分析和趋势图表。
- JSON 备份与恢复。
- 正式发布、部署和完整用户体验验收。

因此，本次成果应定义为“V0.1 本地 Web 原型”，不能视为完整正式版本。

## 二、AI Software Studio 流程验证

### 需求理解阶段

结论：成功。

有效做法：

- 从产品目标出发，先识别用户、场景和 V0.1 边界。
- 将“本地运行”“不接外部接口”“不直接编码”作为明确约束。
- 逐步确认平台、攀岩类型、难度体系、记录单位和完成状态。

遇到的问题：

- 初始“本地移动端”被理解为 Android 原生应用，但用户真正目标是验证工作室流程，而非立即完成原生交付。
- 对“移动端”的交付形态澄清得不够早，导致技术路线发生一次较大调整。

经验：需求澄清必须区分“目标设备”“交付载体”和“本次验证目标”。

### 技术方案阶段

最初方案为 Kotlin、Jetpack Compose、Room 的 Android 原生应用。开发前环境检查发现本机缺少 JDK、Android SDK、Gradle 和 ADB，且用户不希望为流程验证修改系统环境。

调整为 Web 方案的原因：

- 当前目标是验证 AI Software Studio 端到端流程。
- Codex 已提供 Node.js v24.14.0 与 pnpm 11.7.0。
- Chrome 与 Edge 已可用。
- React + TypeScript + Vite 能以更低环境成本验证产品、架构、测试和用户体验流程。
- IndexedDB 可以满足本地结构化数据和离线存储需求。

技术调整本身合理，但说明环境检查应发生在技术方案定稿之前或同步进行。

### 开发阶段

使用技术栈：

- React 19、TypeScript 6、Vite 8。
- pnpm 11.7.0。
- IndexedDB 与 idb。
- Vitest、fake-indexeddb、oxlint。

开发过程：

1. 创建项目骨架及 PRD、技术方案、测试计划。
2. 先实现难度体系和完成状态领域规则。
3. 使用自动化测试锁定规则。
4. 实现 IndexedDB Repository 与 CRUD/筛选基础。
5. 实现移动端优先的快速记录、统计、历史列表和删除。
6. 启动本地服务供用户直接体验。

开发中出现的问题：

- pnpm store 被生成到仓库根目录，需要诊断和清理。
- TypeScript 6 的严格语法配置暴露了构造函数参数属性问题。
- 中文内容曾出现编码损坏，导致 JSX 受损。
- `App.tsx` 被压缩为单行后，增量补丁多次匹配失败。
- 多轮只汇报“下一步”而没有立即交付实际修改，降低了协作效率。

### 测试阶段

测试方式：

- 领域规则单元测试。
- IndexedDB Repository 自动化测试。
- fake-indexeddb 模拟浏览器数据库。
- oxlint 静态检查。
- TypeScript 类型检查与 Vite 生产构建。
- 本地 HTTP `200` 检查。
- Edge 浏览器人工体验入口。

验收结果：

- 3 个测试文件通过。
- 16 项自动化测试通过。
- lint 通过。
- production build 通过。
- 本地页面可以访问和保存数据。
- 用户已开始体验，但完整用户验收结论尚未形成。

## 三、本次成功经验

### 有效的工作室规范

- 先需求、PRD、技术方案、风险评估、开发计划，再进入编码，有效避免了无目标开发。
- 开发前检查路径、Git、版本、权限和运行实例，及时发现 Android 工具链不满足。
- 问题必须先诊断再修复，帮助定位 pnpm store、TypeScript 和编码问题。
- 修改后必须运行测试、lint 和 build，避免把静态错误带入体验版本。
- 用户只负责产品体验，技术验证由 AI 承担，角色边界正确。

### 提高效率的流程

- 先写领域规则和测试，再实现数据层与界面。
- 使用固定难度表和强类型模型，避免跨难度体系错误。
- 使用 Repository 隔离 IndexedDB，让数据逻辑可测试。
- 通过本地开发服务器快速进入用户体验验证。

### 避免的错误开发

- 没有在缺失 Android 环境时盲目创建无法验证的原生工程。
- 没有为了测试项目而修改系统环境。
- 没有接入不必要的远程服务或 API。
- 没有把抱石和难度攀登的难度直接换算或混合统计。

## 四、问题与不足

- 移动端交付方式不足：当前是浏览器本地 Web 原型，尚未形成可安装 PWA 或移动端安装包。
- 部署流程不足：缺少静态构建物发布、版本地址、缓存策略和部署验收流程。
- 发布流程不足：缺少版本标签、发布报告、回滚验证和正式发布门禁实践。
- API 接入流程不足：本项目未接 API，尚未验证权限、密钥、限流、失败降级和隐私审查。
- Agent 自动化不足：多个步骤依赖人工连续输入“继续”，未形成稳定的里程碑自动推进机制。
- 交付节奏不足：存在多轮只描述下一步而没有实际执行的情况。
- 文件维护不足：缺少统一格式化规则，导致单行源码和补丁匹配问题。
- 编码规范不足：中文文件编码未被自动检查。
- Git 基线不足：项目初始化和业务原型长期保持未提交，降低了阶段可追踪性。
- 完整验收不足：尚未形成测试报告、发布报告和用户体验验收结论。

## 五、AI Software Studio 优化建议

建议在 `CORE_RULES/` 后续新增：

1. `DEPLOYMENT_RULES.md`：定义本地、测试和生产部署方式、构建物、配置、验证及回滚。
2. `RELEASE_RULES.md`：定义版本冻结、测试证据、用户验收、Git tag、发布报告和回滚门禁。
3. `ENVIRONMENT_MANAGEMENT_RULES.md`：定义系统环境、项目内工具链、内置运行时、版本锁定和禁止修改范围。
4. `API_INTEGRATION_RULES.md`：定义 API 选型、密钥管理、权限、限流、错误处理、模拟测试和隐私要求。
5. `SOURCE_FORMAT_AND_ENCODING_RULES.md`：统一 UTF-8、格式化工具、行尾和提交前自动检查。
6. `AGENT_EXECUTION_RULES.md`：要求“继续”触发实际执行；禁止连续输出计划而无产出；定义长任务进度与里程碑交付。
7. `PROJECT_GIT_BASELINE_RULES.md`：要求项目初始化、领域层、数据层和 UI 原型分别建立可回退提交。

流程优化建议：

- 技术方案评审必须同时附带环境可行性检查。
- 项目初始化后应先建立 Git 基线，再进入功能开发。
- 每个里程碑必须输出真实测试结果和未完成范围。
- 用户体验验收前必须明确“原型验收”还是“正式版本验收”。
- 开发服务器、浏览器验收和停止服务应纳入标准操作清单。

## 六、未来产品升级路线

### V0.1：本地 Web 版本

- 完成记录编辑、完整筛选、成长分析和备份恢复。
- 完成响应式视觉优化、自动化测试和用户体验验收。
- 形成可重复运行的本地交付方式。

### V0.2：移动端适配

- 完善 PWA 安装、离线缓存和移动端交互。
- 评估封装为 Android 应用或采用跨平台容器。
- 优化触控、屏幕适配和本地文件备份体验。

### V0.3：天气与 API 接入

- 在用户明确授权后接入天气等辅助信息。
- 按 API 接入规范处理密钥、限流、缓存、离线降级和隐私。
- 保持核心训练记录在无网络时可用。

### V1.0：AI 训练助手

- 基于用户自己的训练历史生成趋势解释和训练建议。
- 明确 AI 建议的边界、置信度和安全提示。
- 为用户保留数据控制权、导出能力和关闭 AI 分析的选择。

## 复盘结论

本项目成功验证了 AI Software Studio 从需求理解、技术调整、环境检查、领域建模、自动测试到浏览器体验的主要流程。最重要的收获是：流程规范能够避免在错误环境和错误技术路线下直接编码，但工作室仍需加强环境管理、Git 阶段基线、格式与编码、部署发布以及 Agent 连续执行规则。
