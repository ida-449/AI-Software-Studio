# 原生功能契合与回归诊断隔离

> 分类：DEVELOPMENT_LESSONS
> 验证状态：已通过自动测试与本地浏览器回归验证
> 适用范围：在已有业务系统中增加轻量能力

## 背景与目标

已有系统新增功能时，真正的风险通常不是功能本身，而是重复建设入口、控件、数据源和错误体系，导致页面割裂、维护成本上升，并让外部环境故障被误判为代码回归。

## 有效做法

1. 先分析原系统的信息架构、数据粒度、查询控件、表格、加载状态和错误方式。
2. 优先在原有标签、下拉或查询卡片中增加一种查看方式，不新建平行导航和数据系统。
3. 复用原登录态、接口、缓存和真实数据粒度；只新增纯数据整理与显示适配层。
4. 将可测试的筛选、去重、聚合、缺失值和格式化逻辑放入纯函数，浏览器层只负责交互和渲染。
5. 回归按层隔离：静态检查 → 纯逻辑测试 → 模拟接口 → 本地浏览器 → 外部真实依赖。
6. 网络、授权、平台限流或环境缺失应单独标记，不能直接判定为代码失败；已有可用数据可以降级展示时必须明确说明。

## 经验结论

- “与原系统契合”应作为功能验收项，而不是实现后的视觉修补。
- 缺失值必须保留缺失语义，不得为了聚合方便伪造为零。
- 同名业务对象缺少平台唯一 ID 时，必须带上账号或主体范围进行区分。
- 环境故障与代码回归分层诊断，可以减少无效修复和对稳定代码的误改。

## 不适用范围

- 原系统没有可复用数据源、权限模型或交互框架时，可以独立设计，但仍需先证明不能复用。
- 涉及不可逆外部提交时，不能因为追求一步完成而取消安全门禁。
